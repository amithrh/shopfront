# AskOnce infrastructure (AWS CDK, Python)

One stack, **`AskOnceCore`**, in **ap-southeast-2** only (the project Region; `app.py` refuses any other).
Every resource is tagged `project=askonce`.

| Resource | Details |
|---|---|
| DynamoDB `askonce` | Single table. `pk`/`sk` (S); GSIs `gsi1` (owner inbox by status), `gsi2` (commitment by task id), `gsi3` (expiry sweep), each `gsiNpk`/`gsiNsk` (S), projection ALL; TTL `expires_at`. On-demand, PITR off. |
| DynamoDB `askonce-tasks` | SEP-2663 task store. `taskId` (S); GSI `byPrincipal` (`principal`/`createdAt`, ALL); TTL `expiresAt`. Same as `mcp_tasks.dynamodb.table_definition()`. On-demand, PITR off. |
| Secrets Manager (4) | Request-state key, owner-link key, id key, admin token. Generated by Secrets Manager (64 alphanumeric chars), injected as `ASKONCE_*` secrets, never in code or the template. |
| ECR `askonce-mcp` | Immutable tags, scan on push, keeps the last 10 images. |
| Logs `/askonce/mcp` | 7-day retention. |
| ECS cluster `askonce` + Express Mode service `askonce-mcp` | `AWS::ECS::ExpressGatewayService` with our own arm64 Fargate task definition (0.5 vCPU, 1 GB, container `Main` on port 8000, health `/health`), 1 task. Express Mode creates the HTTPS load balancer, certificate, `*.ecs.ap-southeast-2.on.aws` URL and scaling. Only created when the `image_tag` context is set. |
| Task role | DynamoDB `GetItem`, `BatchGetItem`, `Query`, `PutItem`, `UpdateItem`, `DeleteItem` on `askonce` (+ its indexes), and `GetItem`, `PutItem`, `Query` on `askonce-tasks` (+ index). Nothing else. |

The container runs with `ASKONCE_ENV=prod` and `ASKONCE_STORAGE=dynamodb`. `ASKONCE_ALLOWED_HOSTS`,
`ASKONCE_ALLOWED_ORIGINS`, `ASKONCE_CORS_ORIGINS` and `ASKONCE_PUBLIC_BASE_URL` all name the service URL.

**Why two deploys the first time.** The Express URL only exists once the service does, but the server
must know its public host before it accepts `/mcp` traffic. The first service deploy uses the placeholder
`pending.invalid` (the container starts and `/health` is green; `/mcp` answers 421). The second passes
the real host from the `ServiceEndpoint` output. `deploy.sh` does both. The host never changes after that
unless the service is replaced.

**Profiles.** In DynamoDB storage the server reads profiles from the table, not from files.
`scripts/seed_dynamodb.py` publishes `profiles/live/`: the three demo businesses as certified by the
deterministic certifier (`scripts/certify_demo.py`, verdicts in `profiles/certification/`). The image also
carries them in `/app/profiles-live` for memory-storage runs.

## Prerequisites

- AWS profile `shopfront` with access to the project (Region ap-southeast-2), Docker with buildx, `uv`,
  Node.js (for `npx`), the AWS CLI.
- A default VPC in ap-southeast-2 (Express Mode uses it when no network configuration is given).
- CDK bootstrap, **once per account/Region** (not done by any script here):
  `AWS_PROFILE=shopfront npx -y aws-cdk@2.1143.0 bootstrap aws://<account-id>/ap-southeast-2`

Pinned versions (all published before 2026-09-28): `aws-cdk-lib==2.270.0`, `constructs==10.8.1`, CDK CLI
`aws-cdk@2.1143.0`.

## Commands

```bash
cd infra
uv sync                                                    # CDK libraries into infra/.venv
JSII_SILENCE_WARNING_UNTESTED_NODE_VERSION=1 uv run pytest -q   # synth-level tests (no AWS calls)

# Synthesize (no credentials needed)
npx -y aws-cdk@2.1143.0 synth                              # core layer only
npx -y aws-cdk@2.1143.0 synth -c image_tag=abc123 -c public_host=<host>.ecs.ap-southeast-2.on.aws

# Deploy everything (idempotent: core layer, build + push the arm64 image, service, real host)
AWS_PROFILE=shopfront ./deploy.sh

# Seed the certified live profiles (profiles/live/) into the table (once, or after re-certifying).
# From the repo root. boto3 needs botocore[crt] for `aws login` profiles (friction log #12), hence `uv run --with`.
server/.venv/bin/python scripts/seed_dynamodb.py --dry-run                           # validate only
AWS_PROFILE=shopfront uv run --project server --with "botocore[crt]==1.43.111" \
  python scripts/seed_dynamodb.py

# Admin token (to mint owner links) without printing it into shell history
aws secretsmanager get-secret-value --profile shopfront --region ap-southeast-2 \
  --secret-id "$(aws cloudformation describe-stacks --profile shopfront --region ap-southeast-2 \
    --stack-name AskOnceCore --query "Stacks[0].Outputs[?OutputKey=='AdminTokenSecretArn'].OutputValue" --output text)" \
  --query SecretString --output text | pbcopy
```

Manual equivalent of `deploy.sh`: `cdk deploy AskOnceCore` (core layer), build and push
`server/Dockerfile` with `docker buildx build --platform linux/arm64 ... --push`, then
`cdk deploy AskOnceCore -c image_tag=<tag>`, read the `ServiceEndpoint` output, and
`cdk deploy AskOnceCore -c image_tag=<tag> -c public_host=<endpoint>`. Always pass the current
`image_tag` on later deploys: a deploy **without** it removes the service.

## Teardown

```bash
cd infra
AWS_PROFILE=shopfront CDK_DEPLOY_REGION=ap-southeast-2 npx -y aws-cdk@2.1143.0 destroy AskOnceCore
```

Everything in the stack is deleted, **including both tables and their data** (they use
`RemovalPolicy.DESTROY`; the data is demo data, reseedable with `seed_dynamodb.py`), the ECR images
(`empty_on_delete`) and the log group. The four secrets go into Secrets Manager's default 30-day
recovery window (no charge for them after deletion is scheduled). The CDK bootstrap stack (`CDKToolkit`)
stays; delete it from the CloudFormation console if you no longer use CDK in this Region.

## Cost note (approximate, ap-southeast-2, check the AWS Pricing Calculator)

With the service running 24/7 at one task:

| Item | ≈ per month |
|---|---|
| Fargate arm64, 0.5 vCPU + 1 GB | $15–18 |
| Application Load Balancer (Express Mode, shared by up to 25 services) | $18–20 + LCUs (≈ $0 at demo traffic) |
| Public IPv4 addresses (load balancer per AZ + task) | $10–15 |
| Secrets Manager, 4 secrets | $1.60 |
| DynamoDB on-demand (demo traffic), ECR storage, CloudWatch Logs (7 days) | < $2 |
| **Total** | **≈ $45–55 / month, ≈ $1.50–1.80 / day** |

That is a large share of the $100 Free-plan credits over the 10 days to the deadline. Ways to cut it:
destroy the stack between demo sessions (the core layer alone, without the service, costs about $2/month),
or deploy the service only on demo days (`deploy.sh` restores it in about 5–10 minutes; the URL changes
when the service is recreated).
